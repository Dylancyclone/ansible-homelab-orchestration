Pelican Wings is the daemon half of the Pelican game-server stack. It talks to the host Docker socket and creates, starts, stops and destroys the individual game-server containers on command from [Pelican Panel](../pelican_panel/).

## Setting up

Deploy [Pelican Panel](../pelican_panel/) first and finish its installer, then:

```yaml title="inventories/homelab/group_vars/homelab.yml"
pelican_wings_enabled: true
```

By default, Wings can be accessed at `http://[your_server_ip]:8104` or `https://wings.[your_domain].com` if you have [DNS access](../../guides/dns-access/) configured.
You do not browse to Wings yourself — that address is what the Panel and the in-browser console connect to.

### Required one-time manual step

Wings' `config.yml` is **generated by the Panel**, so this role cannot template it. Until the file exists the role deliberately does not start the container (it prints instructions instead), because Wings exits without a config and would otherwise sit in a restart loop.

1. In the Panel, go to **Admin → Nodes → Create Node** and set:
   - **FQDN**: `wings.[your_domain].com`
   - **SSL**: **HTTPS with (reverse) proxy**, *not* plain "HTTPS (SSL)". The proxy variant sets `behind_proxy: true` in the generated config so Traefik terminates TLS and Wings speaks plain HTTP behind it. Pick the plain-SSL option and Wings will try to do its own TLS and the Panel will not be able to reach it.
   - **Port**: `443`. This is the *panel-facing* connect port and the form sets it for you in proxy mode. The separate **Listen Port** (`8080`) is what Wings binds inside the container, which is what this role's Traefik label points at — leave it alone.
   - **Daemon SFTP Port**: `2022`
2. Open the new node's **Configuration** tab and save the generated YAML on the Wings host as `[docker_home]/pelican_wings/etc/config.yml`.
3. Edit the four paths in that file so they match the host paths this role bind-mounts (see [Identical host and container paths](#identical-host-and-container-paths) below):

   ```yaml title="[docker_home]/pelican_wings/etc/config.yml"
   system:
     data: [data_home]/pelican/volumes
     tmp_directory: [docker_home]/pelican_wings/tmp
     user:
       passwd:
         directory: [docker_home]/pelican_wings/etc
     machine_id:
       directory: [docker_home]/pelican_wings/etc/machine-id
   ```

4. Re-run the role (`--tags pelican_wings`). Wings starts and the node should show as connected in the Panel.

## Configuration

See the default configuration options for Pelican Wings at [`roles/pelican_wings/defaults/main.yml`](https://github.com/Dylancyclone/ansible-homelab-orchestration/blob/main/roles/pelican_wings/defaults/main.yml).
Add any overrides to your `inventories/[your_inventory]/group_vars/homelab.yml` file.

### Ports

- `pelican_wings_port` (8104 → container 8080) is the Wings API and the browser console websocket. It is routed through Traefik at `wings.[your_domain].com`, LAN-only via the `blockExternal` middleware unless you set `pelican_wings_available_externally: true`.
- `pelican_wings_sftp_port` (2022) is the in-panel SFTP file manager. This is raw TCP and cannot go through Traefik's HTTP proxy, so it is published directly on the host: connect to `sftp://[your_server_ip]:2022` with your Panel credentials.
- The **game** ports are not managed here at all. Each server gets its ports allocated in the Panel, and those are the only ports you should forward at your router — never the Panel or Wings ports.

### Disk layout

Wings' config, logs and tmp live on the docker pool under `[docker_home]/pelican_wings/`, and per-server game data (worlds, saves) lives on the data pool at `[data_home]/pelican`.
Each server ends up under `volumes/[server-uuid]/`, so the folders are named by UUID rather than by game: identify servers in the Panel UI rather than by browsing the directory.

### Identical host and container paths

Wings runs as a container here and talks to the host Docker socket, which is "Docker-out-of-Docker": the game servers are siblings of the Wings container, not children.
That has one consequence worth knowing about, because it is the single most confusing failure in this stack.

When Wings launches a game server (or the one-shot installer), it asks the **host** Docker daemon to create the container, passing bind-mount source paths *as Wings sees them inside its own container*.
The host daemon then looks for those exact paths on the host. So every directory Wings re-exports has to exist at the **same absolute path both inside the Wings container and on the host**, which is why this role mounts three directories at identical paths rather than at the image's defaults:

1. the game-data `volumes` directory,
2. the install-script `tmp` directory, and
3. Wings' own **config** directory, because it generates the `passwd`/`group` files for the in-container user and `machine-id` in there and re-exports those too.

The third one is easy to miss: get it wrong and installs succeed while every server fails before boot with `bind source path does not exist: /etc/pelican/passwd`.
Because the config directory is no longer at the image's baked-in `/etc/pelican`, the role also overrides the container command to point `--config` at the real path.
The log directory is the one thing that does *not* need mirroring — per-server logs are written into each server's own data directory, so it is never re-exported.

If `config.yml`'s `system.*` paths disagree with the mounts, you get `bind source path does not exist` errors: either the install hangs forever, or the server crash-loops before boot.

### Docker networks and subnets

This role creates a dedicated `wings0` bridge for the game-server containers, pinned to `172.31.0.0/16`.
Wings also self-creates a network from the `docker.network` section of `config.yml`, whose upstream default sits in the same `172.18`–`172.21` range that Docker's automatic subnet assignment climbs through — so it can collide with a network Docker assigned to something else you already run.
If a network fails to create, or containers cannot reach each other, suspect an overlapping subnet first.

Because stopping Wings does not stop the game servers attached to `wings0`, disabling the role removes the Wings container but tolerates the network removal failing while servers are still up. Re-run it once they are stopped and the network goes away.

### Steam-based games

Two things bite on the first SteamCMD-based server (Valheim, Ark, Rust, CS, Satisfactory and so on), and neither is a problem with this role:

- **DNS.** `config.yml`'s `docker.network.dns` list defaults to public resolvers and is injected into the install/game containers. If that resolver returns a bad answer for the Steam CDN, SteamCMD fails with `KeyValues Error ... '<!DOCTYPE'` and "Steamcmd needs to be online to update." Point it at a resolver that works for the Steam CDN on your network. Re-check this whenever you recreate the node, since it lives in the Panel-generated config.
- **Transient install failures.** Steam intermittently refuses to hand out the anonymous app-info token, which surfaces as `Failed to install app 'N' (Missing configuration)`. The stock eggs run `steamcmd` exactly once, so a single bad pass leaves you with a silently empty install that the Panel reports as successful. Wrap the `+app_update` call in a retry loop in the egg's install script (Panel → **Admin → Eggs**), looping until SteamCMD prints `Success! App 'N' fully installed` and exiting non-zero if it never does. Note that install scripts live in the Panel database, so re-importing an egg loses the change.

### Security

Wings mounts `/var/run/docker.sock`, which is effectively root on the host.
This is inherent to how Wings works and is not something this role adds — a host-installed Wings mounts the socket too.
Anyone with administrative access to your Panel can, in effect, run containers on the host, so treat Panel admin accounts accordingly and keep the Panel off the public internet unless you have a reason not to.

### Upgrading

The image version is **pinned** and the container is excluded from [Watchtower](../watchtower/).
Wings and the Panel share a compatibility contract, so bump `pelican_wings_image_version` and `pelican_panel_image_version` to matching releases and re-run both roles together.
